컨테이너 재시작2,973회0회
기동실패 반복17.1초
ERROR 로그기동마다 발생0건
문제
약 3일 21시간 동안 메인 서버 장애 시 서비스를 넘겨받을 서버가 없었습니다.
울산 스탠바이 백엔드가 재시작을 2,973회 반복했습니다.
Standby drift 워크플로 경고가 발생했지만 3일 이상 지나 확인했습니다.
원인
서버 시작 시 실행되는 전적 백필이 SELECT ... FOR UPDATE를 실행했습니다.
스트리밍 복제본은 읽기 전용이라 SQLSTATE 25006으로 실패했습니다.
이 백필은 Flyway와 스케줄러 비활성화 설정과 무관하게 실행됐습니다.
판단
pg_is_in_recovery()는 복제 상태만 판별해 제외했습니다.
스케줄러 설정 연동은 DB 쓰기 가능 여부와 무관하고 승격 전 재기동 시 재발해 제외했습니다.
해결
트랜잭션 시작 직후 SHOW transaction_read_only가 on이면 백필을 건너뜁니다.
로컬 PostgreSQL 17 복제 환경에서 실패를 재현했습니다.
pg_promote() 승격 후 백필이 실행되는 것까지 확인했습니다.
결과
2026-11-15 Mac mini 감시 스크립트에 스탠바이 응답 점검(5분 주기)을 추가했습니다.

2026-11-06 ~ 07JPA

문제
같은 회원이 커뮤니티 글을 다시 열 때마다 조회 수가 올랐습니다.
작성자 본인 조회도 포함됐습니다.
서비스를 직접 사용하며 발견했습니다.
1차 수정 반영 후 약 20시간 동안 작성자와 재조회 회원의 글 상세가 500을 반환했습니다.
원인
중복 조회를 거르는 기록이 없었습니다.
1차 수정의 조회 기록 쿼리에 붙은 @Modifying(clearAutomatically = true)가 영속성 컨텍스트를 비웠습니다.

해결
조회자당 1행인 조회 기록 표(post_views)를 추가했습니다.
처음 기록될 때만 조회 수를 올리고 작성자, 운영진, 비로그인 조회는 제외합니다.
500 장애는 조회 기록을 먼저 실행하고 게시글을 조회하도록 순서를 바꿔 해결했습니다.
개발 서버에서 수정 전 500, 수정 후 200을 확인하고 통합 테스트를 추가했습니다.
결과
같은 원인의 장애가 2회째였습니다.
clearAutomatically 사용 시 쿼리 전에 조회한 엔티티를 다시 쓰는지 확인하는 리뷰 기준을 장애 기록에 추가했습니다.

원인
빈 공간 운전 판정이 운영 시작 1시간 전 시각을 dt.time(h0 - 1, 30)으로 만들었습니다.
운영 시작이 0시면 -1시가 되어 ValueError가 발생했습니다.
이 계산은 전체 건물을 한 번에 처리해 건물 1곳의 오류가 API 전체를 중단시켰습니다.
핸들러가 내부 ValueError를 400으로 변환해 서버 결함이 요청 오류로 표시됐습니다.
인자가 없는 API도 같은 오류를 반환해 화면 요청 가설을 제외했습니다.
해결
06:25 해당 건물의 운영 시작을 01시로 바꿔 임시 복구했습니다.
판정 함수를 시각 조회 없이 계산하도록 수정했습니다.
06:40 배포 후 06:41 운영 시간을 원래 값으로 복원했습니다.
결과
운영 시작 0시 건물을 포함한 회귀 테스트 2개를 추가했습니다.
수정 전 코드에서 운영 서버와 같은 오류 문구로 실패하는 것을 확인했습니다.

문제 정의

학교, 기업 통학버스 이용자는 버스 지연과 정류장 변경을 미리 확인하기 어렵습니다.

기존 버스 위치 서비스는 버스마다 GPS 단말기와 통신 장비를 설치해야 해서 도입 비용이 큽니다.

2024 하드웨어 버전은 IoT 단말기로 위치를 수집했습니다.
2025 소프트웨어 버전은 운전자 앱 GPS만 사용해 버스에 설치하는 기기를 없앴습니다.

1

수신한 버스 위치의 DB 미반영

2024-10-15SpringMongoDB
항목수정 전수정 후
위치 DB 반영미반영5초 주기 반영
DB 쓰기수신마다 1회버스당 5초 1회
문제
승객 앱 지도의 버스 위치가 갱신되지 않았습니다.
단말기가 WebSocket으로 보낸 버스 위치가 MongoDB에 저장되지 않았습니다.
원인
원인은 3개였습니다.
같은 클래스 내부에서 호출하는 메서드의 @Transactional은 Spring 프록시를 거치지 않아 적용되지 않았습니다.
배치 저장 스케줄러는 @EnableScheduling 누락으로 실행되지 않았습니다.
갱신 쿼리의 컬렉션 이름 bus가 엔티티 선언 Bus와 대소문자가 달랐습니다.
판단
Spring Data MongoDB에는 JPA 변경 감지가 없습니다.
따라서 갱신 로직에서 저장 호출을 명시적으로 유지했습니다.
해결
수신한 위치는 ConcurrentHashMap에 버스별 최신값 1개만 보관합니다.
5초 주기 배치가 보관한 값을 저장합니다.
스케줄링 설정과 컬렉션 이름도 수정했습니다.

학교 인증 코드 오판정

2024-11-20외부 API권한
항목수정 전수정 후
틀린 인증 코드인증 완료거부
판정 기준HTTP 상태 코드응답 본문 success
문제
틀린 인증 코드를 입력해도 학교 인증이 완료됐습니다.
이 경우 GUEST 사용자가 USER 권한으로 승급됐습니다.
원인
외부 학교 이메일 인증 API(univcert)는 실패 응답에도 상태 코드 200을 반환했습니다.
기존 코드는 상태 코드 200만 확인했습니다.
판단
외부 API의 성공 여부는 HTTP 상태 코드가 아니라 응답 본문 필드로 확인하도록 기준을 바꿨습니다.
해결
응답 본문의 success 값으로 성공 여부를 판정합니다.
권한 승급은 success가 true일 때만 실행합니다.
